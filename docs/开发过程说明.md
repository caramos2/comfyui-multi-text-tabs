# 开发过程说明

> 本文档说明 Multi-Text Tabs 的研发模式与验证链路，供关注项目工程实践的读者参考。

## 1. 项目定位

本项目是一个面向 ComfyUI 的自定义节点，目标是改善工作流中「多份文本需要分别维护」的
操作体验：为每一份待命文本提供独立的输出端点，并额外提供一个随当前选中项变化的
「主输出」端点。

项目从个人工作流中的实际使用痛点出发，经需求拆解、架构设计、分阶段实现、真机验收
四个环节完成，最终以 MIT 协议开源。

## 2. 研发模式

本项目采用 **AI 辅助开发（AI-Assisted Development）** 模式。

需要明确说明的是：项目方向、需求定义、验收标准与最终发布决策均由项目方确定并负责；
AI 工具在开发过程中承担了代码实现、测试编写、文档整理与缺陷排查等执行性工作。

| 环节 | 负责方 | 说明 |
|---|---|---|
| 需求定义 | 项目方 | 目标场景、优先级与取舍均由项目方判断 |
| 架构设计 | 双方协作 | AI 产出设计方案与约束清单，项目方审核确认后执行 |
| 代码实现 | AI 辅助 | 按已确认的方案实施，每阶段完成后提交验证 |
| 测试与验收 | 双方协作 | AI 编写自动化测试，项目方在真实环境中复核关键链路 |
| 发布决策 | 项目方 | 开源协议、仓库可见性与发布节奏由项目方决定 |

### 2.1 需求如何进入开发流程

项目方的使用反馈以「问题描述 + 期望行为」的形式进入开发流程，由 AI 负责转化为
可验证的技术条目（验收清单），再进入实现阶段。需求原文不纳入本仓库的公开文档，
以避免将非必要的个人表述带入公开记录。

### 2.2 架构约束的确定方式

在实现之前，先完成一轮 **P0 技术验证**（详见 [P0-技术验证报告.md](P0-技术验证报告.md)），
目的是确认所依赖的 ComfyUI 前端扩展接口确实可用、以及计划架构是否存在隐含的
序列化歧义。验证结论直接决定了后续架构：

- 确认节点可以只保留 **一个** DOM widget，同时承载标签栏与编辑区，
  从而避免多 widget 的顺序 / 位置歧义；
- 确认后端 `RETURN_TYPES` 槽位数量不可变，因此把「端点数量随文本数变化」这一需求
  全部收敛到前端实现；
- 确认后端解析连线时 **只依据端点序号**，不依据端点名 —— 这一事实直接决定了
  「主输出」必须固定置于端点列表末尾，以免既有工作流的连线发生错位。

### 2.3 分阶段推进

项目按 P0 → P5 推进，**每个阶段都以真机验证为完成条件**，不以静态代码审查替代：

| 阶段 | 内容 | 完成标志 |
|---|---|---|
| P0 | 技术验证与架构定型 | 前端构建产物实测，关键 API 事实确认 |
| P1 | 最小可用节点 | 节点可注册、连线可用、属性可序列化 |
| P2 | 状态机与 widget 桥接 | 状态管理独立可测，无 DOM 依赖 |
| P3 | 标签栏 UI 与交互 | 增删改切复制、快捷键、菜单可用 |
| P4 | 输出端点模型改造 | 端点数量 / 名称随文本同步 |
| P5 | 验收、文档与开源 | 真机链路复核、测试全绿、文档齐备 |

### 2.4 需求演进中的一次架构反转

v1.2 引入「每条文本一个输出端点」后，**计划书原定的架构发生反转**：

- 原计划：仅当前活动文本进入后端，其余文本留在前端；
- 实际：每条文本都有独立输出，因此 **全部文本都必须送达后端**。

这一反转带来明确代价 —— 改动任意一条待命文本都会使该节点的执行缓存失效。
该代价已在 [变更说明.md](变更说明.md) 与 README 中如实记录，未作回避。

## 3. 验证体系

### 3.1 自动化测试

测试分三层，共 80 项，全部可离线运行：

| 层次 | 文件 | 项数 | 覆盖内容 |
|---|---|---|---|
| 后端契约 | `tests/test_nodes.py` | 15 | 载荷解析、逐字透传、槽位与端点名映射 |
| 状态管理 | `tests/frontend/state.test.mjs` | 34 | 标签增删改切复制、ID 唯一性、损坏修复 |
| 前端端到端 | `tests/frontend/check_extension.mjs` | 31 | 假 DOM 下的完整节点行为与连线簿记 |

第三层的做法值得说明：测试脚本将 **实际发布的前端文件** 载入 `node:vm` 上下文，
配合一个有边界的假 DOM 运行，因此「被测文件」与「被发布文件」是同一个文件。
假 DOM 同时复刻了真实前端的 reactive `node.properties` 机制与输出端点 API，
包括「连线按槽位序号登记」这一非直观行为。

### 3.2 真实环境验收

自动化测试无法覆盖的部分，通过在真实 ComfyUI 环境中复核：

- 端点数量与名称是否与待命文本一致；
- 切换标签后主输出送出的内容是否随之改变（以实际提交与产物逐字节比对确认）；
- 增删待命文本时，既有连线的槽位序号是否自动跟随；
- 工作流存盘、载入、复制粘贴后的状态恢复是否完整。

### 3.3 由真机验收发现并修复的缺陷

有一类缺陷仅在真实环境中暴露，静态审查与假 DOM 测试均无法捕获：

1. 前端内部将连线保存在 `Map` 中且不提供按 ID 查询的接口 —— 按数组下标取值会
   **静默失败**，不抛异常但连线重编号失效；
2. 连线实际登记在 `link.origin_slot` 上，端点上的 `links` 只是按序号推导出的
   **派生视图** —— 插入端点后视图立即错位；
3. LiteGraph 的 `addOutput` 仅在末尾追加，而 `removeOutput` 会自行将后续连线的
   序号减一 —— 插入与删除需要采用不同的处理策略。

这三点现已全部纳入回归测试。

## 4. 代码规范与边界

为保证插件在 ComfyUI 环境中的可预期性，开发过程中确立了以下不可违反的约束：

- 文本逐字透传：不拼接、不 trim、不做提示词插值（`dynamicPrompts=False`）；
- 工作流文件是唯一的持久化来源，不使用 `localStorage` / `sessionStorage`；
- 只使用 ComfyUI 官方文档化的扩展接口，不修改 `LGraphNode.prototype` 等核心原型；
- 用户输入一律以 `textContent` 写入 DOM，不使用 `innerHTML`；
- 样式全部限定在 `.mtt-*` 作用域内，不影响 ComfyUI 界面其余部分；
- 后端与前端职责严格分离，前端不重复存储后端已持有的数据。

相关约束同样适用于后续贡献者，详见 [CONTRIBUTING.md](../CONTRIBUTING.md)。
