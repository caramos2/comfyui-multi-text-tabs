## 2. 关键 API 事实（均来自本机前端构建产物，非记忆）

### 2.1 DOM Widget

- `node.addDOMWidget(name, type, element, options)` 存在，且 **ComfyUI 核心自己就在用**
  （`core-CsX6xQKw.js` 中的 `AUDIO_UI` / `AUDIO_RECORD` / `WEBCAM`）。
- `options.getValue / setValue / getMinHeight / getHeight / getMaxHeight` 有效；
  `getMinHeight` 可避免每帧 `getComputedStyle` 测量。
- **`widget.value` 的 getter 就是 `options.getValue()`**（`readDomWidgetValue`）。
  → 编辑器内容即 widget 值，**不存在"最后一次输入丢失"的竞态**，这正是计划书 §2.1 最担心的问题。
- `widget.serialize === false` 的 widget 不进入 `widgets_values` / `widgets_values_named`；
  `widget.options.serialize === false` 的 widget 不进入执行请求。两者是**不同**的开关。

### 2.2 自定义 widget 类型（计划书未提及，但决定了最终形态）

- 扩展的 `getCustomWidgets()` 返回 `{ 类型名: (node, inputName, inputSpec, app) => ({widget}) }`。
- 注册表按 **input 的 type 字符串**匹配：`registerCustomWidgets` → `inputIsWidget(type)`。
- 因此可以在 `beforeRegisterNodeDef` 里把某个 input 的类型改写成自定义类型，
  让它由 DOM widget 承载，而**保留 input 名字**。
- `options.socketless = true` → **不生成输入插口**（`addInputWidget` 里的 `if (!p.options.socketless)`）。
  这正是核心 `AUDIO_UI` 的做法。

### 2.3 持久化语义（决定架构的地基）

- `node.properties` 是 **canonical field**：保存时 `t.properties = cloneObject(this.properties)`，
  载入时 `for (let t in e.properties) this.properties[t] = e.properties[t]`。
  → **计划书把标签数据放 `properties` 是正确的**，且会被深拷贝。
- 工作流文件里同时写两种 widget 值：
  - `widgets_values`：位置数组，**只含 `serialize !== false` 的 widget**；
  - `widgets_values_named`：`{ widget名: 值 }`。
- 载入时 `createWidgetRestorationState` **优先按名字恢复**。
  → **widget 顺序不影响取值**，插入/重排 widget 不会串位。
- 执行请求 `graphToPrompt` 按 **widget 名字**组装 `t[i.name] = value`，
  跳过 `options.serialize === false` 的 widget。
  → 只有活动标签的文本会进后端，标签集合不会。

### 2.4 节点复制

- `LGraphNode.clone()` = `createNode(type)` → `serialize()` → `cloneObject` → `configure()`。
  → 副本走的是"新建 + 还原"，**每个副本有独立的 DOM 元素与独立的 properties 深拷贝**。
- `properties` 深拷贝 ⇒ 副本标签集合互不影响。

### 2.5 properties 是 Vue reactive 对象（P0 阶段漏掉的关键事实）

本条**不在**前端构建产物的静态文本里，是真机运行时从
`Object.getOwnPropertyDescriptor(LGraphNode.prototype, "properties")` 读到的：

```
get properties(){ return this._state.properties }
set properties(e){ if(e!==this._state.properties){ for(let e of Object.keys(this._state.properties)) delete this._state.properties[e]; Object.assign(this._state.properties,e) } }
```

`this._state` 是 Vue 的 reactive state ⇒ `node.properties` 本身是 reactive 代理，
读回来的子对象也是代理。于是：

```
node.properties[KEY] = X      // 写入原始对象
node.properties[KEY] === X    // false —— 读回来的是 reactive(X)，不是 X
```

**后果**：任何"用 `===` 判断对象有没有被换掉"的写法**永远为假**。
v1.0 的状态层正是这么写的，于是每次读状态都会重新归一化并整体替换
`properties[KEY]`，一次操作里先后拿到的两个状态对象里，前一个成了孤儿，
改动全写进了没人引用的对象 —— 表现为"点 ＋ 加不出标签、编辑区被清空"。
v1.1 改用藏在状态里的**不可枚举标记（marker）**做身份判定，绕开代理包装。

### 2.6 事件冒泡与 widget 回调

- DOM widget 的 `widget.value` setter 走 `options.setValue(v)` 然后 `this.callback?.(this.value)`；
  但本前端 `widget.callback` 默认 **undefined**，不主动赋值就等于没有回调。
- 画布变更跟踪的官方写法（核心 dynamic group widget 同款）：
  `graph.beforeChange()` → `canvas.emitBeforeChange()` → 改动 →
  `graph.afterChange()` → `canvas.emitAfterChange()` → `node.setDirtyCanvas(true,true)`。
- `root.addEventListener(name, handler, true)`（捕获阶段）里的 `stopPropagation()`
  会让事件**到不了标签栏**，双击重命名与右键菜单因此不可用。

### 2.7 动态输出端点（v1.2 新增，实测得出）

主人要求「输出端点数量与待命文本数量统一，端点名与文本名同步」，
为此在真机上逐条验证了 LiteGraph 的输出端点 API：

- **`addOutput(name, type)` 的参数顺序是「先名称、后类型」**。
  本机前端（1.58.5）实测原型：
  `addOutput(e,t,n){let{links:r,...i}={...n},a=Object.assign(new NodeOutputSlot({name:e,type:t},this),i);...}`
  → 第一个参数进 `name`，第二个进 `type`。
  ★ 这条如果搞反，节点右侧会显示一排 `STRING`、且类型变成中文标题，**连线直接失效**。
- `node.outputs` 是普通数组，可以直接改 `output.name` / `output.type` 实现改名；
  `node.removeOutput(index)` 从尾部删除。
- **后端 `RETURN_TYPES` 的长度不可变**：ComfyUI `execution.py` 用
  `RETURN_TYPES[slot]` 校验连线索引，输出数量一变旧连线就会错位。
  → 结论：**后端固定 16 个 STRING 槽**，动态的部分全部放在前端。
- 端点变多后需要 `node.setSize()` 抬高节点，否则端点会挤在一起。

本机真机实测（验收工作流，4 节点）：
2 条待命文本 → 2 个端点（`待命文本 1` / `角色设定`）；
点 ＋ → 3 条待命文本 → 3 个端点，名称同步为 `待命文本 1` / `角色设定` / `待命文本 3`；
新文本自动成为当前文本、编辑区为空可输入；widget 值为三条正文组成的 JSON 数组。

## 3. 最终架构（与计划书的差异已说明）

```
后端 nodes.py
  required: texts : STRING (multiline, dynamicPrompts=False)  ← JSON 数组，一条待命文本一个元素
  output   : 待命文本 1..16 : STRING  ← 固定 16 槽；空槽返回空串，不拼接、不 trim

前端 web/multi_text_tabs.js
  beforeRegisterNodeDef : 把 texts 的 type 改写为 MULTI_TEXT_TABS_UI
  getCustomWidgets      : 用一个 DOM widget 承载「标签栏 + 编辑区」
                          options.socketless = true   → 无多余输入插口
                          options.serialize = true    → 进执行请求（全部文本都要能取到）
                          widget.serialize  = false   → 不进工作流文件（正文只在 properties）
  syncOutputs()         : 按待命文本条数增删/改名输出端点，并抬高节点
  node.properties.multi_text_tabs = { version, active_id, tabs[] }  ← 正文唯一权威副本
```

### 与计划书的差异及理由

| 计划书 | 实际实现 | 理由 |
|---|---|---|
| 原生 textarea widget + 另一个 DOM widget 放标签栏 | **单个** DOM widget 同时承载标签栏与编辑区 | 避免 widget 顺序/位置数组歧义；`widget.value` 直接读实时文本，天然解决 flush 竞态 |
| `tabs_data` 不进后端 | **v1.2 反转：全部待命文本进后端**（widget 值 = JSON 数组） | 「每条文本一个输出端点」要求每条文本都能被下游取到，这是必然代价；执行缓存会随任意一条文本变化而失效 |
| 编辑区是"原生多行编辑器" | 自绘 `<textarea>`（同一个 DOM widget 内） | 仍是一个标准多行文本编辑器，但值由我们自己掌控 |
| 单个输出 `text`（计划书未设想多输出） | **每条待命文本一个输出端点**，名称与文本名同步 | 主人 v1.2 明确要求：端点数量与待命文本数量统一，便于看清传出的是哪一串文本 |
